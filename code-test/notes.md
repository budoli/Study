## Day 001 - 두 수의 합 인덱스

- 사용한 접근: HashMap/Map/dict에 `숫자 -> 인덱스` 형태로 저장하고, 현재 숫자에 대해 `target - 현재값`이 이미 있는지 확인했다.
- 시간 복잡도: O(n)
- 공간 복잡도: O(n)
- 막혔던 부분:
  - 처음에는 `인덱스 -> 숫자` 형태로 저장하려고 해서 필요한 값을 빠르게 찾기 어려웠다.
  - Java의 `HashMap`, JavaScript의 `Map`, Python의 `dict` 사용법이 아직 익숙하지 않았다.
  - 같은 숫자가 여러 번 나올 수 있으므로 값을 key로, 인덱스를 value로 저장해야 한다는 점을 확인했다.

## Day 002 - 압축 문자열 길이

- 사용한 접근: 문자열을 왼쪽부터 보면서 연속된 같은 문자 그룹의 개수를 세고, 그룹이 끝날 때 압축 길이를 더했다.
- 시간 복잡도: O(n)
- 공간 복잡도: O(n)
- 막혔던 부분:
  - 그룹별로 count를 세는 접근이 처음에 어려웠다.
  - 마지막 문자 그룹을 반복문이 끝난 뒤 따로 처리해야 한다는 점을 놓쳤다.
  - `count == 1`이면 숫자 `1`을 붙이지 않아야 한다는 조건을 주의해야 했다.
  - Java는 `char[] cha = s.toCharArray()`를 쓰면 공간 복잡도가 O(n)이 되고, `s.charAt(i)`를 쓰면 O(1)로 줄일 수 있다.
  - JS/Python도 문자열을 배열/리스트로 바꾸지 않고 인덱스로 접근하면 공간 복잡도를 O(1)로 줄일 수 있다.

## Day 004 - 회의실 배정

- 사용한 접근: 회의를 종료 시간 기준으로 정렬하고, 현재 회의의 시작 시간이 마지막 선택 회의의 종료 시간 이상이면 선택했다.
- 시간 복잡도: O(n log n)
- 공간 복잡도: O(1)
- 막혔던 부분:
  - 시작 시간 기준이 아니라 종료 시간 기준으로 정렬해야 하는 이유가 처음에 헷갈렸다.
  - `lastEnd`를 반복문 안에서 매번 새로 만들면 안 되고, 마지막으로 선택한 회의의 종료 시간으로 유지해야 했다.
  - 종료 시간이 같을 때 시작 시간 기준으로 한 번 더 정렬하는 코드를 익혔다.

## Day 005 - 올바른 괄호 확장판

- 사용한 접근: 여는 괄호는 stack에 넣고, 닫는 괄호가 나오면 stack에서 꺼낸 값과 짝이 맞는지 확인했다.
- 시간 복잡도: O(n)
- 공간 복잡도: O(n)
- 막혔던 부분:
  - Java에서 `HashMap`, `HashSet`, `Stack` 사용법이 아직 익숙하지 않았다.
  - 닫는 괄호가 나왔을 때 stack이 비어 있으면 바로 false를 반환해야 한다는 점을 놓치기 쉬웠다.
  - Java에서는 `stack.pop()` 호출 전에 `stack.isEmpty()`를 먼저 확인해야 한다.
- 다시 풀 날짜: 26/07/21(1)

## Day 006 - 프린터 대기열

- 사용한 접근: 큐에 `[중요도, 원래 인덱스]`를 함께 저장하고, 현재 문서보다 중요도가 높은 문서가 남아 있으면 뒤로 보냈다.
- 시간 복잡도: O(n^2)
- 공간 복잡도: O(n)
- 막혔던 부분:
  - 처음에는 Map으로 인덱스를 매핑하려고 했지만, 같은 중요도가 여러 개 있을 수 있어 위험했다.
  - 문서의 중요도뿐 아니라 원래 인덱스를 큐 원소에 함께 저장해야 location을 추적할 수 있었다.
  - 더 높은 중요도가 남아 있는지 확인하기 위해 큐를 순회하는 구조를 이해했다.
  - 중요도 범위가 1~9로 작으므로 카운트 배열을 쓰면 시간 복잡도를 더 줄일 수 있다는 점을 알았다.
- 다시 풀 날짜: 26/07/22(1)

## Day 007 - 피로도 던전

- 사용한 접근: DFS/백트래킹으로 현재 갈 수 있는 던전을 모두 시도하고, 방문 개수의 최댓값을 갱신했다.
- 시간 복잡도: O(n!)
- 공간 복잡도: O(n)
- 막혔던 부분:
  - 재귀 함수를 어떤 기준으로 호출해야 하는지 잡는 게 어려웠다.
  - `visited`를 DFS 안에서 새로 만들면 방문 기록이 유지되지 않는다는 점을 확인했다.
  - Java에서는 최대값을 관리하기 위해 클래스 변수 `static int answer`를 사용할 수 있고, Python에서는 중첩 함수에서 `nonlocal answer`를 사용할 수 있다.
  - 탐색 후 `visited[i] = false`로 되돌리는 백트래킹 과정이 중요했다.
- 다시 풀 날짜: 26/07/23(1)

## Day 008 - 합이 K인 연속 구간

- 사용한 접근: 투 포인터로 `left`, `right`, `sum`을 관리하며 합이 k보다 크면 왼쪽 값을 빼고, 합이 k와 같으면 개수를 증가시켰다.
- 시간 복잡도: O(n)
- 공간 복잡도: O(1)
- 막혔던 부분:
  - `sum`을 매번 `numbers[left] + numbers[right]`로 계산하려 했지만, 현재 구간합으로 누적 관리해야 했다.
  - `sum > k`인 동안에는 `while`로 왼쪽 값을 계속 빼야 한다는 점이 중요했다.
  - 모든 원소가 양수이기 때문에 투 포인터가 가능하다는 조건을 이해했다.
- 다시 풀 날짜: 26/07/23(1)

## Day 009 - 예산 상한선

- 사용한 접근: 이분 탐색으로 cap 후보를 정하고, `sum(min(request, cap))`이 budget 이하인지 확인하며 가능한 최댓값을 찾았다.
- 시간 복잡도: O(n log m)
- 공간 복잡도: O(1)
- 막혔던 부분:
  - cap을 직접 정하는 값으로 생각해서, 이분 탐색으로 후보를 좁혀간다는 감각이 처음에 어색했다.
  - Java에서 배열의 최댓값을 `Math.max(requests)`처럼 바로 구하려 했지만, 배열은 직접 순회해서 최댓값을 찾아야 했다.
  - Python에서 `/`와 `//` 차이를 놓쳤다. cap은 정수 상한선이므로 `(left + right) // 2`를 써야 한다.
  - `total <= budget`이면 현재 cap은 가능한 값이므로 `answer`를 갱신하고 더 큰 cap을 탐색해야 한다는 방향 판단을 다시 확인했다.
- 다시 풀 날짜: 26/07/27(1)

## Day 010 - 의상 조합 수

- 사용한 접근: Map/dict로 의상 종류별 개수를 세고, 각 종류마다 `count + 1`을 곱한 뒤 아무것도 선택하지 않는 경우 1개를 뺐다.
- 시간 복잡도: O(n)
- 공간 복잡도: O(t)
- 막혔던 부분:
  - 처음에는 의상 이름까지 조합에 직접 사용해야 한다고 생각할 수 있지만, 실제로는 종류별 개수만 필요했다.
  - Python에서 `counts.values`가 아니라 `counts.values()`처럼 메서드를 호출해야 한다는 점을 확인했다.
  - Java에서는 `Map` 값을 증가시킬 때 `getOrDefault(type, 0) + 1` 패턴을 사용해야 했다.
  - 조합 계산에서 각 종류마다 "선택하지 않는 경우"가 있으므로 `count + 1`을 곱하고, 마지막에 전체 미선택 1가지를 빼야 했다.
- 다시 풀 날짜: 26/07/28(1)

## Day 011 - 연결 요소 개수

- 사용한 접근: 무방향 그래프를 인접 리스트로 만들고, 1번부터 n번까지 순회하면서 방문하지 않은 정점을 만날 때마다 DFS를 시작했다.
- 시간 복잡도: O(n + e)
- 공간 복잡도: O(n + e)
- 막혔던 부분:
  - 처음에는 간선을 직접 비교해서 개수를 세려고 했지만, 연결 요소는 간선 개수가 아니라 연결된 정점 묶음의 개수라는 점을 확인했다.
  - 인접 리스트가 `edges`를 DFS/BFS에 적합한 형태로 바꾼 구조라는 감각이 부족했다.
  - Python에서 `for node in (1, n + 1)`은 범위 순회가 아니라 두 값만 순회한다는 점을 확인했고, `range(1, n + 1)`을 사용해야 했다.
  - Java에서는 `static` 메서드에서 함께 쓰는 `graph`, `visited`를 클래스 변수로 선언해야 했다.
  - Java의 `List`는 `graph.get(node)`처럼 접근해야 하며, 배열처럼 `graph[node]` 또는 `graph.get[node]`로 접근할 수 없다는 점을 확인했다.
- 다시 풀 날짜: 26/08/03(1)
